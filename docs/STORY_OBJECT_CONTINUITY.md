# Recurring story-object continuity

The Book Bible now includes inanimate story objects as well as personalized items. A route marker, key, map, vehicle or plot-relevant landmark receives one fixed design and an explicit occurrence schedule. Personal items retain their existing decorative/carry-through policy.

## Data flow

1. `illustrator/storyObjects.js` reads the final manuscript, catalog beats, theme and authored object definitions together. A whole-story extraction resolves object families, aliases, instances, per-spread state and story-criticality. Field-scoped completion fills remaining occurrence gaps without rewriting the identities. Evidence must quote the relevant manuscript/beat exactly; explicit object mentions cannot silently lose their occurrence. Catalog definitions cannot be omitted or rewritten. Invalid data, contradictions and unavailable planning fail with `identity_kit_failed` before spreads render.
2. The plan is elected with create-if-absent storage under `catalog-assets/story-objects/so-1/<input hash>.json`. Retries adopt the stored winner. The fingerprint includes the manuscript, beats, theme, authored definitions and version. Storage outages do not invent a replacement plan.
3. Prop sheets use a design-keyed namespace. The image must pass both the existing sheet content checks and the fixed-design check before election. A missing or unverified critical sheet stops the run. The fixed design remains authoritative over the vision-derived description.
4. Each spread receives the same sheet and design, plus only its scheduled instances and physical state. Groups are intentional; a moved, damaged or repaired instance keeps its identity. Plot objects do not inherit the personal-item rule that makes every prop small and decorative.
5. Spread QA verifies appearance, required presence, multiplicity and `state_match` (including stated clues and spatial relationships). The existing repair budgets apply. After repairs, final critical-family contact checks verify the selected artwork across spreads. Missing checks and residual critical defects require `consistency_unresolved` even when `CATALOG_SHIP_ON_EXHAUSTION=1`.

## Authoring a catalog design

Add a book ID entry in `services/catalogEngine/data/storyObjects.json`. Each definition needs `id`, `name`, noun-phrase `aliases`, `critical`, and `design` fields for `shape`, `material`, `colors`, `scale`, and `features`. These fix otherwise unspecified appearance; the final manuscript must not contradict them. Additional manuscript objects are still extracted automatically.

The first authored definition covers `safari_6_7_watering_hole_map`: a knee-high wooden post with one orange stripe on its front face. Multiple route markers share that design; the displaced third marker keeps its instance ID. Occurrence state comes from the actual manuscript rather than a hard-coded twelve-page sequence.

The planner supports up to six object families, twelve instances per family and twelve spreads. Exceeding those bounds requires review; objects are never silently truncated. Generic pronouns resolve within occurrences and are not allowed as ambiguous global aliases.

## Retries, review and rollout

- Planner `so-planner-5` selects evidence using numbered source passages for each spread's manuscript and catalog beat. The worker resolves those IDs to exact original substrings (at most 600 characters) before validation and election, avoiding model transcription errors in quotations, punctuation or whitespace. Unknown IDs and references to a different spread are rejected. Existing elected plans with exact quoted evidence remain valid and keep their cache keys.
- Coverage omissions, ungrounded citations, unknown/empty instance references, and single/group count conflicts are collected together. Once object identities validate, the worker freezes that plan in memory and completes only the defective fields through `storyObjectRepair.js`. It never requests a full-plan rewrite for an occurrence defect. Every completion call retains the entire manuscript and fixed plan as context, including pronouns and off-screen mentions.
- Each object/spread task becomes an explicit required response property. A dynamic [Gemini JSON response schema](https://ai.google.dev/api/generate-content#v1beta.GenerationConfig) restricts fields, source IDs, instance IDs and array bounds. Local validation also checks string bounds, uniqueness, grounding and count consistency before applying each patch. New occurrences get all five state fields; evidence-only fixes cannot alter state or visibility; only an existing single/multiple-ID contradiction permits repairing both membership and multiplicity. A reported story contradiction stops immediately.
- Completion has a separate bounded budget from extraction: at most two extraction calls, then batches of up to eight occurrence tasks with two attempts per batch. Valid patches stay in memory for the rest of the run; the second batch attempt requests only unfinished keys. Malformed responses or missing keys do not trigger another identity extraction. The six-family/twelve-spread bounds cap completion at nine batches. Exhaustion fails before illustrations render and logs the specific unfinished object/spread tasks. Partial plans are never elected or replayed as validated manifests.
- Every occurrence must reference at least one defined instance, even when `required=false`: identity membership is separate from visibility. On new model output only, an empty list can reuse the family’s sole defined instance (including an uncounted group). Otherwise completion selects existing IDs using the source and fixed state; it cannot invent instances, a count, or a default visible occurrence. Elected manifests remain strict and keep their existing cache identities.
- Story-object references get up to three image candidates: a two-view reference, one corrective retry, then a fresh unlabelled single-view portrait. The portrait retains the same fixed design and must pass content/design QA, with exactly one complete object. Design-specified parts and contents count as parts of that object; separate family instances still count separately. A plural family name never requests the entire group. A transient unavailable QA verdict gets one retry on the same image before failing closed. Personal props also receive a third, checked single-view candidate after two content failures, with unlettered controls and no multi-view diagram instructions. Companions retain their two-candidate policy. Existing elected images and specs keep their keys and are reused.
- Failed references are not elected. Existing verified sheets and object plans retain their cache identities, so a checkpoint retry can recover a missing reference without changing the story or replacing successful references. Generation errors include the underlying reference rejection when available in the sheet log.
- The object-plan hash enters the Book Bible/render namespace and each spread's QA record. A changed plan cannot reuse older approval. Current QA records retain the per-object verdicts; unchanged retries reuse the existing pixels.
- Older or unverified object QA is checked again. Reviewed artwork whose pixels change during lettering repair is rechecked for object state as well.
- The admin Book Bible exposes story-object sheets through the existing Props list; its JSON also contains the full plan, occurrence evidence and storage identity. Probe callbacks report critical failures through existing advisories/unresolved fields.
- Legacy PDF-only rebuilds preserve their existing artwork and namespace. Explicit illustration regeneration upgrades an existing book to object locks. This change alone does not repair or regenerate already-created books.
- Added model work is one text planning pass per changed manuscript plus bounded completion when needed, cached reference-sheet work per design/theme/style, and a final contact check per critical family. Automated tests mock model/storage calls; live visual quality and generation latency still require a staging book run.
- Before rollout, ensure `CATALOG_PROP_SHEETS` and `CATALOG_CONTACT_QA` are enabled. Disabling those layers does not permit critical story objects to ship unchecked.

## References that heal themselves (2026-09-16)

The reference path no longer pauses a book on its own verdicts (`docs/CHILDREN_VISUAL_RECOVERY.md`, same date). Behind `CATALOG_REFERENCE_AUTOHEAL` (default on; `0` restores every pause exactly):

- **Ladder → second opinion → re-plan → degrade.** The three durable candidates are unchanged. A `design_matches` / `representation_matches` rejection needs a second agreeing opinion (`CATALOG_REFERENCE_JUDGE_QUORUM`, default 2; asked once at thinking level `LOW`, its own durable call, label `prop-reference-second-opinion`). An exhausted ladder — or an elected reference that fails re-verification — gets ONE re-plan (`CATALOG_REFERENCE_REPLAN_ROUNDS`, default 1, 0–2): a strict-JSON text call (label `reference-replan`, `catalog-assets/reference-replans/v1/{sha}`) that may only rewrite the design within the closed vocabulary (`shape`, `material`, `colors`, `scale`, `features`, 1–180 characters each — never for a catalog-authored object) and/or downgrade the contract to `single` with a description naming one representative member. The new design/contract re-keys `valueHash`, so the ladder runs fresh; the round persists at `<election>.replans/<objectId>/r<n>.json` and is applied on every later read. When that fails too — or the judge outcome is a provider block, an exhausted budget or a configuration hold — the object DEGRADES to a described object (no sheet; its design in the PROPS block; a `storyObjects` advisory `reference degraded: <name> — <reason>`; `degraded: true` on the prop in `bookBible.props[]` and on the plan object). A critical degraded object keeps presence, count, lettering and state blocking; its `look` is advisory (`degradedObjectAdvisories`), and the cross-spread set gate skips it.
- **The elected plan keeps its identity.** `resolveStoryObjects` applies persisted re-plans to `objects` and keeps the originals on `renderObjects`; the plan `hash` is still the election's, markers keep matching, and the scene-presence audit runs on the original contract (its saved request never moves) with the re-plan re-applied afterwards. `bookBible.storyObjects.replans` lists every round in force.
- **A stored plan that stopped validating** is re-planned under a retry fold of its election key (`<inputHash>-r<n>.json`, the existing 2-attempt budget). If planning still fails on the plan itself, the catalog seeds become the plan — the authored design, one instance per family, one grounded required occurrence per spread whose manuscript or beat names the family (`seedPlan`; a book without seeds is the explicit no-object plan) — elected at the fold with `fallback: {kind: 'catalog_seeds', reason}` and a `storyObjects` advisory, so no later run spends on it again. A planner outage still throws; an outage never invents a plan. With the switch off, `contract_conflict` pauses as before.
- **Explicit regeneration** (`forceNew` / `forceRerender` → `identityRetry` → `retryNamespace`) opens fresh candidate slots (`{png}.candidates/retry-<hash>/N.png`) and a fresh verification root, and re-asks a saved block on the contract / presence calls under `…/retry-<hash>`; a plain resume replays; an elected sheet wins either way.
- Tests: `__tests__/services/catalogEngine/{propSheet,bibleIndex,storyObjects,scenePresence,visualRecovery}.test.js` (mocked providers; state and reuse, not artwork quality).
